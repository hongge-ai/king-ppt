## 1. 目标与文件

目标不是把一份通用长提示词整体塞进 system prompt，而是将“模板风格分析 → 按风格生成 → 渲染对照验收”拆成可独立调用的三个阶段，通过结构化风格画像传递规则。

对用户仍表现为“上传参考 PPT，输入新内容，生成同风格 PPT”。拆分发生在系统内部。

| 文件 | 职责 | 预期输出 |
| --- | --- | --- |
| [analyze-template.md](../src/prompts/analyze-template.md) | 从结构证据和真实页面图提取风格、版式家族、组件、负向约束与实现风险 | 新增 `styleModel` 的 JSON 草案 |
| [generate-slide.md](../src/prompts/generate-slide.md) | 根据选定家族、已确认内容和编译契约生成或修复单页 | 完整 SVG 字符串 |
| [audit-slide.md](../src/prompts/audit-slide.md) | 分别检查同内容复刻、新内容风格迁移和 SVG→PPTX 导出保真 | 问题与修复路由 JSON |

三个提示词覆盖封面、目录、章节、正文、图文、观点、指标、图表、表格、对比、流程、时间线、架构、矩阵、公式、代码、案例、总结、结束和附录。该目录是检查范围，不是要求每份成品都包含全部页型。

## 2. 仓库现状与关键判断

以下是上述基线提交的代码审查结论；不是本次新增功能，也不是端到端实测结果。

### 2.1 保留 SVG-as-IR，不引入第二套权威页面表示

[spec.js](../src/spec.js) 和 [normalize.js](../src/normalize.js) 已明确以完整 SVG 保存每页，预览与导出使用同一份清洗后的 SVG。旧的版式载荷不应被本方案重新引入。

职责应区分为：

- 风格画像规定“怎么设计”。
- 页面计划规定“这一页使用哪一种设计、填入什么”。
- SVG 保存“最终画出来什么”。

不额外维护一份需要与 SVG 双向同步的权威 `scene_graph`。导出编译器内部生成场景对象属于实现细节，可以继续保留。

同源 SVG 可以减少差异，但本身不保证不同渲染器的最终画面相同；仍需重新渲染 PPTX 验证。

### 2.2 只改自由 SVG 提示词，不一定影响上传模板主路径

[server.js](../src/server.js) 的整册和单页生成先尝试 `renderTemplateSlide()`；有画像且确定性渲染成功时，不会调用 `generateSlideSvg()`。因此，只替换 [generate-deck.js](../src/generate-deck.js) 的逐页提示词，不足以改变上传模板的主要生成行为。

单页生成中的 `feedback` 当前传给自由 SVG 分支，没有传入确定性模板渲染调用。因此，在确定性分支成功的情况下，提示词增强本身不能使该分支理解用户修改意见。接入时应让两条路径都处理修改意图。

### 2.3 需要补强版式家族，而不只是配色与字体

[template-profile.js](../src/template-profile.js) 已有角色、源页、颜色、字体和几何测量；现有 `families` 更接近逐页测量记录，还不是可执行的多版式家族库。

[template-renderer.js](../src/template-renderer.js) 的正文有卡片、编号、顶部强调条和底部结论条等通用布局倾向，并对部分条目数量与文本长度进行截取。这些是代码行为，不能指望提示词自动覆盖。

这些组件可以成为特定家族的实现，但不能成为所有上传模板的默认设计语言。颜色和字体相同，不代表信息组织、密度和视觉关系相同。

### 2.4 创作规则必须与编译器实际能力对齐

[spec.js](../src/spec.js) 的文字规则允许部分分组变换，而 [svg-to-pptx.js](../src/svg-to-pptx.js) 的分组展开主要处理平移；多边形也存在近似映射。

因此，提示词采用保守子集：复杂几何展开为明确路径，不依赖未实现的变换、继承和浏览器特性；文字显式换行并提供文本框尺寸。提示词约束只能降低风险，不能替代编译器修复。

### 2.5 机械高分不能替代视觉检查

[style-score.js](../src/style-score.js) 主要检查颜色、字体、标题位置、图片存在性和正文标题一致性。[既有迭代记录](style-iteration-log.md) 已记录机械分高但视觉结果不好的情况。

结构检查、视觉评审和最终 PPTX 渲染是不同证据。视觉模型同样可能误判，应要求它输出可观察的问题、依据与根因假设，而不是把其主观评分作为绝对真值。

### 2.6 参考重建图、SVG 截图和真实 PPTX 渲染必须区分

[render-deck-sheet.js](../scripts/render-deck-sheet.js) 渲染的是保存下来的 SVG，而不是导出的 PPTX。[bake.js](../src/bake.js) 通过解析对象并重建 HTML 生成底图。

二者都可以用于检查，但不能被标记为已经验证目标办公软件中的真实结果。图像证据必须携带来源和渲染方式；解析器丢失的元素不能被误当成参考稿原本没有。

## 3. 总体设计与数据边界

建议沿用现有模板存储，新增扩展，不覆盖原始测量：

```text
template-profile.json
  原有字段                     保持兼容，保留原始测量和资产
  styleModel                   新增：规则、家族、组件、证据、未知项

每页 slide.meta
  familyId                     选定的版式家族
  variantId                    选定的构图变体
  referencePageIndexes          对应的 0-based 参考页索引
  styleModelVersion            本次锁定的画像版本
```

[normalizeSlide()](../src/normalize.js) 已保留 `meta`，但上述字段和消费逻辑仍需实现。`styleModel` 应新增自己的版本和校验规则，不改写现有画像 `version` 的含义。

现有 `theme.tokens`、画像 `tokens` 和新 `styleModel.tokens` 不应直接混用：需要显式映射颜色格式、语义名称、字号与几何单位。

### 保持四个顶层角色

继续使用：

```text
cover / section / content / closing
```

在角色之下增加 family 与 variant。例如：

```text
role: content
familyId: analytical
variantId: chart-with-insight

role: content
familyId: technical
variantId: equation-with-annotation
```

这些名称只是组织方式示例，不是为所有模板固定规定的家族。

可继承 [原模板系统设计文档](template-system-design.md) 中的 family+variant、容量模型与组件语义思想，但应落实到当前 SVG 路径，不恢复旧的权威页面载荷。

### 建议的生成决策

```text
确认内容并选择页面家族
    |
    v
有适配该家族的确定性实现吗？
    |-- 有：使用该实现，按真实槽位填充
    |-- 无：使用同一份 styleModel 约束 SVG 生成
    |
    v
统一清洗、结构检查、视觉检查
    |
    v
导出 PPTX，并在目标环境重新渲染检查
```

不能再仅凭“存在 profile”就将所有正文交给同一种布局。也不能因为参考没有出现公式页，就突然引入另一套模板：应从既有规则推导，并单独标记和验收。

确定性实现负责已知家族的稳定表达，模型负责尚未编码的布局表达；二者共享同一套设计依据。

## 4. 三阶段调用契约

以下是待实现的编排协议，不是已存在的 API。

### 4.1 模板分析阶段

建议在导入、重新分析或升级画像时调用一次，不在每一页生成前重复分析。

调用方需要提供：原始来源清单、现有结构测量、整套缩略图、代表页大图、工具真实能力，以及品牌和比例策略。仓库现有 [llm.chatVision()](../src/llm.js) 可以作为多模态入口，但本次没有新增它的调用点。

分析输出写入 `styleModel` 前，应新增 JSON Schema 或等价的确定性校验，至少检查字段类型、稳定 ID、枚举、页索引范围、家族引用、颜色、单位、未知值以及资产引用。当前提示词中的字段清单不是已经实现的验证器。

视觉估计、结构事实、跨页推导和回退值应明确区分。模型判断与原始测量矛盾时，保留两者及纠正建议，不静默覆盖原始证据。

### 4.2 页面规划与生成阶段

编排层先生成 `pagePlan`，选择 family/variant，映射内容与槽位并准备资产，再调用生成器。页面计划本身可由后续独立模块实现，本次没有交付该模块。

发送给单页生成器的上下文以本页相关规则为主：选定家族、组件、全局锁定项、参考原型、内容与编译契约。不要每页无差别重复整套参考图与全部规范。

确定性实现应报告容量不足，而不是截断字符串。自由 SVG 输出同样需要内容完整性与容量检查。

单页提示词的成功输出固定为裸 SVG；缺数据、缺公式资产、不支持的比例、容量冲突等失败不应混进 SVG 结果。编排层需在调用前拦截或通过独立错误通道处理；生成后发现缺项则拒收并重新规划，不把空白页或占位符当成完成。

`feedback` 应映射到页面计划、家族、资产或局部 SVG 修改，并进入两条渲染路径。全局规则更新后应复查所有受影响页面，不逐页补丁造成漂移。

### 4.3 验收阶段

三种模式分别调用并分别记录：

| 模式 | 比较对象 | 不得混淆 |
| --- | --- | --- |
| `reconstruction` | 相同内容的参考页与重建页 | 可以检查几何与断行，但图像指标必须真实计算 |
| `style_transfer` | 新内容页面与对应参考家族 | 内容变化不是像素错误；配色相同也不是风格通过 |
| `export_fidelity` | 最终清洗后 SVG 渲染与导出 PPTX 的重新渲染 | 没有 PPTX 渲染证据就标记未验证 |

视觉模型输出必须经过结构校验。修复路由应区分提取、风格画像、页面计划、模板渲染器、SVG 生成器、资产处理、清洗器、编译器与验证工具。

`pass` 只适用于实际检查过的模式与范围。可编辑能力应结合 PPTX 对象结构检查，不仅依靠截图。缺少必要证据的阶段标记 `unverified`，不能汇总成“全链路通过”。

建议默认最多 3 轮生成—检查—修正；达到预算后保留未解决问题，不宣称完美完成。

## 5. SVG 与编辑能力约束

### 5.1 能力契约优先于浏览器表现

以 [svg-sanitize.js](../src/svg-sanitize.js)、[svg-to-pptx.js](../src/svg-to-pptx.js) 和实际渲染测试共同确定能力契约。不能把“清洗后没有删除”视为“导出会正确处理”。

当前提示词保守要求包括：

- 用明确 path 表达复杂几何，不依赖多边形近似或未支持变换。
- 每个元素显式声明样式，不依赖分组继承。
- 不使用 defs/use、滤镜、渐变、蒙版、裁切、CSS、脚本、动画或外链资源。
- 用独立 text 实现每行文字，提供实际 `data-box-w`，不依赖二次自动换行。
- 预处理图片比例与裁切，不假设浏览器 `preserveAspectRatio` 与导出端完全一致。
- 复杂公式先通过可靠工具处理，再转换为可支持的表示；不能未经验证直接嵌入含 defs/use/transform 的公式 SVG。

这些规则不表示源模板不能有复杂效果。分析器仍需如实记录它们，再决定可验证的近似或局部图像化，并说明损失。

### 5.2 单位与比例

区分源文件英寸、源字号 pt、SVG 用户单位和目标 PPTX 尺寸。当前生成提示词按 `1280×720` 工作，不表示非 16:9 参考已获完整支持。

非 16:9 模板必须明确适配或阻断，不能静默拉伸。字体单位转换、基线和文本框内边距应由工具层统一，并用实际字体渲染验证。

### 5.3 编辑能力分层

图片、矢量图片、独立文字/形状与原生语义对象必须分开声明。

用 SVG 形状画出的图表，不等于含可编辑数据的原生图表；用文字和线条拼出的表格，不等于原生表格；公式路径或图片，也不等于原生公式。

保存数据和 LaTeX 源有助于重建，但不能据此宣称最终 PPTX 已有语义编辑能力。整页图片不得作为无说明的通用降级方式。

品牌保留、只学习风格与更换品牌也要明确区分；不得把旧主题文案、联系方式或二维码永久烘焙进新稿。

## 7. 验证方案与实施顺序

### 第一轮原型

至少选三份结构明显不同的参考稿，而不只用一个深色科技模板。例如：品牌规范型、编辑排版型和高密度分析型。具体样本以有权使用的实际文件为准。

用同一组测试内容覆盖封面、章节、正文、图表、表格、公式和结尾。未在参考中出现的页型标记为推导。核心问题是：系统是否学到了不同模板的设计规则，还是把所有模板都转换成了同一套卡片。

增加长标题、中英文混排、负数、多位数字、长标签、多行公式和多节点流程等压力样例；不要把极端测试素材混入正式交付。

### 建议实施顺序

1. 固化能力契约、单位映射和结构校验；为当前 SVG→PPTX 限制建立最小回归样例。
2. 接通模板分析与 `styleModel` 持久化，保留原画像和回退路径。
3. 接通家族选择、容量检查与两条生成路径的反馈处理。
4. 接通图像化验收和 PPTX 重新渲染，明确缺失环境的未验证状态。
5. 在多模板、多页型测试中迭代规则；全局修复后回归相关家族。

验收时分别记录内容完整性、风格一致性、导出保真和编辑能力。任何一项关键错误都不能被综合高分抵消。

## 8. 本次交付边界

本次交付了可阅读、可版本管理的三份提示词原型及其仓库接入设计。

没有新增运行时加载器、模型调用、JSON Schema 验证器、页面规划器、家族路由、公式预处理器、PPTX 渲染服务或视觉评分任务；没有修改现有 JavaScript、配置、依赖、前端构建产物或测试结果。

提示词效果和上述接入方案尚未通过实际 PPT 的分析—生成—转换—复测验证。下一阶段应以具体失败案例迭代，而不是预先承诺“任意 PPT 完美复刻”。
